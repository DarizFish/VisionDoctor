# VisionDoctor —— 多模态机器视觉软件诊断与修复智能体

> **当前比赛版本（2026-09-12）**：场景固定为视觉引导抓取，故障覆盖完整任务。
> 方向见 [抓取诊断计划](design/grasp-diagnosis.md)，实测与自审见 [当前进度](design/PROGRESS.md)，
> 方案与 Demo 的差距见 [比赛方案草案](design/grasp-competition.md)。
> 下文保留历史介绍；其中八段链式定界、诊断后才能读源码等描述已由当前设计替代。

> 让机器视觉工程师用一次持续会话，把**现象、代码和现场**连接成可审计的诊断、修复与验证闭环。

从 3C 装配到汽车焊装、从锂电极片到药品包装，视觉系统承担着定位引导、缺陷检测、字符识别、
装配校验与分拣计数——它是产线的眼睛。一旦视觉软件算错，错误会立刻变成物理动作：抓偏、装错、
误判、停线；而定位一个视觉软件故障所花的时间，往往远超修复它本身。

机器视觉产线出问题时，工程师通常要在截图、日志、代码仓库和现场设备之间来回切换，凭经验定位
根因，再手动改代码、重新跑一遍验证。VisionDoctor 把这条链路收进一个会话：你描述现象、把图片
和日志直接发进来、连上项目仓库，系统会自己复现问题、定位根因、写出修改建议，并在隔离环境里
用可量化的指标验证效果，最后把结论交给你审批。

**代码改不改、上不上线，始终由你决定。VisionDoctor 从不自动合并任何变更。**

## 它是怎么想问题的

诊断一个视觉故障，难的从来不是"猜一个原因"，而是**说清楚为什么不是别的原因**。
VisionDoctor 的整个设计都围绕这一点：

**一、外部世界只有一个入口——观察证据包。** 一次运行的全部现场材料打成一个包：图像、深度、
算法输入输出、日志、配置、轨迹、任务结果。每件材料记录 `sha256`、采集时刻和时钟域，
读取时逐件校验。产品不从别处取数，模型也读不到清单之外的东西。

**二、视觉链路被切成八段，逐段定界。** 工件与来料 · 光学成像 · 采集与时间链路 · 视觉算法 ·
任务结果，这五段任何视觉系统都有；标定配置 · 变换接口 · 机器人侧，这三段在视觉输出被执行
机构消费时才存在。每段只有三种状态：还没查 / 已排除 / 有嫌疑。**非"还没查"的判定必须引用
证据，而且必须是宿主真正交付过的证据**——模型自称看过而没有调用工具的，引用会被丢弃。

**三、一句话推进一轮，工具由宿主执行并记账。** 模型不能自己声称做过什么；它请求，宿主执行，
结果和交付清单一起进账本。你展开任何一轮，都能看到它究竟读了哪几件证据。

**四、四道硬门。** 诊断门（没有定界就看不到源码）、审批门（没人拍板补丁就不生效）、
外部动作门、现场复核门。门是代码算的，不是模型声明的，也不是人口头宣布的。

**五、隔离复跑与现场复核是两件事。** 复跑只证明改过的代码算出了链路本来想要的结果；
**只有改动应用之后新采集的证据**才能说工位恢复了。产品不允许前者冒充后者。

目标架构与实施记录见 [`design/architecture.md`](design/architecture.md)、
[`design/implementation.md`](design/implementation.md)。

## 适合谁使用

- **机器视觉 / 机器人视觉工程师**：位姿估计漂了、检测框错了、识别结果不对，需要快速定位是哪次
  代码改动引入的问题。
- **产线软件维护人员**：现场只有截图、报警日志和一个跑不通的版本，需要一份有依据、可复查的
  排查结论。
- **设备与工艺工程师**：需要先判断到底是软件问题，还是机械、标定或来料的问题。
- **视觉算法团队负责人**：希望每一次修复都留下可追溯的证据链，而不是口头结论。

### 它面向哪一类故障

视觉软件的故障形态跨行业、跨任务反复出现，共性是**都发生在"成像看起来正常"之后**，因此大多
躲得过常规单元测试：

| 故障类型 | 常见形态 |
|---|---|
| **坐标与标定** | 手眼外参失效或方向写反；单位、轴向、四元数顺序混淆；工具 TCP 偏移与基准系变更 |
| **检测与识别** | 阈值漂移导致漏检误检；类别混淆与小目标丢失；后处理顺序变更改变结果 |
| **数据链路** | 时间戳错位、帧与位姿不同步；坐标系约定两端不一致；预处理或通道顺序被改动 |
| **配置与换型** | 换型后参数未同步；多工位配置串用；标定文件版本与代码版本错配 |

这类问题真正难的地方不在"看不见"，而在**看见了也说不清是哪一行代码**：现场信号高度分散
（截图在手机、日志在工控机、代码在仓库），常规测试用理想数据构造、覆盖不到真实配置，
结论多为口头传递、换个人就要从头再来。

典型场景（本仓库的[示例工程](#示例工程)正是这一例）：某次提交之后，机械臂抓取位置偏了约
0.9 米，而项目自带的单元测试全部通过。你把现场照片和日志发进会话，连上仓库，VisionDoctor
复现问题、找到坐标变换写反的那一行、给出修改并补上回归测试，在仿真里重新验证，误差回到
毫米级。

## 多模态输入

VisionDoctor 的诊断证据不只是文字，你可以在同一个会话里持续补充多种材料，系统会逐个真正分析
而不是仅仅存档：

| 输入类型 | 支持格式 | 系统会做什么 |
|---|---|---|
| **现场图片** | PNG、JPEG、WebP | 由视觉模型逐张分析，给出可见观察、诊断相关性、局限和置信度 |
| **日志与文本** | TXT、LOG | 提取内容并结合上下文分析异常线索 |
| **结构化数据** | JSON | 解析后分析字段与数值异常 |
| **文档** | PDF | 提取可检索文本参与分析 |
| **打包材料** | ZIP | 在内存中检查，提取其中的文本、代码、配置和日志 |
| **深度相机数据** | RGB + 深度 + 相机内参 | 参与位姿复现与几何验证 |
| **仿真现场** | Gazebo 采集的场景 | 一键附加到当前会话作为可复现证据 |
| **项目代码** | 任意结构的 Git 仓库 | 自动识别组件、资产、运行方式与验证方式 |

图片和附件的分析结论会在工作台上以「从图片中观察到」「从附件中分析到」卡片呈现，注明依据和
局限。**这些都是诊断线索，不决定修复是否通过**——通过与否由独立的验证程序判定。

## 快速开始

### 环境准备

| 项 | 要求 | 说明 |
|---|---|---|
| 操作系统 | Windows + PowerShell | 其他平台未验证 |
| Python | 3.11 | |
| Git | 任意近期版本 | 候选补丁在**独立 git worktree** 里复跑，跑完删掉，原仓库检出不动 |
| 一个 OpenAI 兼容的对话模型 | 必需 | 见下方「配置模型」，支持工具调用即可 |
| Docker | **不需要** | 诊断与复跑路径不依赖容器 |

### 安装

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev,api,web]"
```

### 配置模型

在项目根目录创建 `.env`（可参考 [`.env.example`](.env.example)），或直接设置环境变量。
对话与视觉都走 **OpenAI 兼容协议**，换服务商只改 base URL 和模型标识：

```text
VISIONDOCTOR_LLM_API_KEY=<你的密钥>
VISIONDOCTOR_LLM_BASE_URL=<服务商的 OpenAI 兼容端点>
VISIONDOCTOR_LLM_MODEL=<模型标识>
VISIONDOCTOR_LLM_MAX_TOKENS=32768

VISIONDOCTOR_VISION_BASE_URL=<可与上面相同>
VISIONDOCTOR_VISION_MODEL=<模型标识>
VISIONDOCTOR_VISION_TIMEOUT_S=300
```

对模型的要求只有两条：**支持工具调用**，且输出长度上限不低于 32768。
换服务商只改这两个值，产品侧不用动。视觉那三行也可以指向本机推理端点，
让图片不出本机。

### 启动

两个 PowerShell 窗口分别启动服务和工作台：

```powershell
# 窗口一：服务
.\.venv\Scripts\visiondoctor.exe serve --host 127.0.0.1 --port 8000

# 窗口二：工作台
.\.venv\Scripts\visiondoctor-web.exe
```

浏览器打开 **http://127.0.0.1:8501**。服务是否就绪可以直接看：

```powershell
curl http://127.0.0.1:8000/health     # {"status":"ok","cases":0}
```

案件持久化在 `.runtime/vd-cases/`，一个案件一个 JSON。**服务重启后案件还在**——
证据账、链路判定、假设、补丁、审批和对话上下文都会读回来；唯一不恢复的是重启时正在
进行的那一轮，因为它的线程已经随进程结束了。

## 复现一次完整诊断

仓库里带着一份可直接复现的材料，不需要真实产线，也不需要跑仿真。

**1. 准备演示工位的观察包与项目仓**

```powershell
.\.venv\Scripts\visiondoctor.exe build-gazebo                      # 首次需要，构建仿真镜像
$vd = ".\.venv\Scripts\python.exe -m harness.gazebo.cli"
& $vd bootstrap-project                                            # 生成被诊断的项目仓
& $vd start                                                        # 启动工位
& $vd run                                                          # 跑一次抓取节拍
& $vd export --run-id <上一步给出的 run id> --destination <导出目录>
```

产物落在 `.runtime/gazebo-pick-cell/` 下：`exports/run-<时间戳>-<摘要>/` 是观察包，
`projects/<名字>/` 是被诊断的项目仓。两者由包里的 `project_revision.commit` 关联，
**接错仓会在连接时被拒绝**。

工位的详细说明见 [`harness/gazebo/README.md`](harness/gazebo/README.md)。
如果不方便跑仿真，可以直接看第 3 步——那是一次真跑留下的全部记录。

**2. 在工作台上走一遍**

| 步骤 | 操作 | 会看到什么 |
|---|---|---|
| 新建诊断 | 左侧 `＋ 新建诊断` | |
| 接入观察包 | 右侧「观察证据包」填 `exports/run-...` 目录 | 工件数与证据条数 |
| 连接仓库 | 右侧「项目仓库」填 `projects/...` 目录 | 提交号由观察包指定，不用你填 |
| 描述现象 | 输入框：`工位机器人抓取位置不对，每次停留在工件上方一定距离，分析一下原因` | 工具调用逐条流式长出来 |
| 看定界 | 右侧诊断链路 | 某一段 suspect、其余 cleared，各自挂着证据号 |
| 让它修 | 输入框：`现在分析源码并尝试修复` | 门通过后才读得到源码；候选补丁与隔离复跑结果 |
| 审批 | 候选修复卡片填审批人 → 批准 | 补丁被提交进仓库，给出落地 commit |
| 现场复核 | 改动应用后重新采集一次，填新包目录 | 改动前后逐件对照 |

**3. 一次真实运行的完整留痕**

`docs/运行证据/` 下有一次真跑的全部记录——观察包构成、会话全文、
八段判定与依据、变换链核算的四列残差、候选补丁、审批与落地 commit、现场复核，
以及刻意触发的六条拒绝路径。上面每个数字都可以用该目录 `_raw/` 里的接口原始返回核对。

## 一次完整的使用流程

1. **描述现象**：新建诊断，用自己的话说，不需要整理成表单，也不需要判断是哪次改动出的问题。
2. **交材料**：输入框左侧的 `＋` 直接附图片和日志；一次运行的观察证据包在右侧填目录接入。
   材料都会登记为证据，**但只有诊断助手真的读过才算数**——证据清单里标着哪些被真正交付过。
3. **连接项目仓库**：填本地文件夹路径。提交号由观察包指定，你不用填；仓库里没有那个提交
   会被当场拒绝，因为那说明源码和证据不是同一次运行。
4. **一句话推进一轮**：每轮结束你会看到本轮的判定、假设和这一轮究竟调了哪些工具。
   上下文跨轮累积，不用重复解释。
5. **过诊断门**：至少一段被指认、至少一段被排除、假设挂着证据——三条都满足，源码工具面才开。
6. **拿到候选补丁**：模型读绑定提交下的源码、提交整份新文件，宿主算 diff 并在独立工作树里
   用这一包**自己的**输入复跑。
7. **审批**：填审批人后批准，补丁被提交进仓库并给出 commit；退回则不写任何东西。
   **合入主线和部署到工位是你的动作**，产品只记录"已应用"的时刻。
8. **现场复核**：改动应用之后重新采集一次，接进来做逐件对照。

## 工作台功能说明

| 区域 | 说明 |
|---|---|
| **左侧边栏** | 所有诊断会话按项目归组，可随时回到任意历史会话继续 |
| **中间对话区** | 发送文字和附件（＋ 在输入框内）；每一轮可展开看这一轮调了哪些工具、交付了哪些证据 |
| **右侧 · 诊断链路** | 八段的当前判定、引用证据和依据 |
| **右侧 · 当前假设** | 每条假设指向哪一段、挂着哪些证据 |
| **右侧 · 候选修复** | 补丁全文、冻结哈希、审批人输入与批准/退回；批准后显示落地 commit |
| **右侧 · 现场复核** | 标记已应用、接入改动后新采集的包、逐件对照 |
| **右侧 · 证据清单** | 共多少条，其中多少条被真正读取过 |
| **右侧 · 观察包与项目仓库** | 接入与连接入口，连上后变成只读卡片 |

发消息后立刻能看到自己的消息，工具调用以流式逐条出现，不必等一轮跑完。

## 出错时会怎样

宁可明确失败，也不给一个假装成功的结论。以下都是产品的原话：

| 情形 | 产品的回答 |
|---|---|
| 观察包与仓库错配 | `这个仓库里没有 992b0f34… 这个提交——观察包和源码很可能不是同一次运行` |
| 诊断门未通过时看工具面 | 只有 `read_evidence`、`check_transform_chain`；源码工具**不在清单里** |
| 绕过清单强行调源码工具 | `诊断门未通过，源码不可见：no segment is implicated；…` |
| 模型引用没读过的证据 | 引用被丢弃，判定降级为 `untested`——这一轮不作废，但拿不到没根据的结论 |
| 读一条不存在的证据 | `EV-999 is not in this case`，失败会记账并显示给人看 |
| 补丁未经审批 | `passed=False　no one has decided on this plan` |

诊断门通过后工具面从 2 件开到 5 件。完整记录见
`docs/运行证据/07_异常与拒绝/`。

## 仿真现场（3D）

没有真实产线也可以完成完整验证。VisionDoctor 内置 ROS 2 + Gazebo + MoveIt 2 + UR5e 仿真环境：

```powershell
.\.venv\Scripts\visiondoctor.exe build-gazebo
.\.venv\Scripts\visiondoctor.exe gazebo-view
```

仿真工位与产品是**隔离的两套东西**，代码在 [`harness/gazebo/`](harness/gazebo/README.md)，
不 import 产品、也不走产品的接口。它的唯一产出是观察证据包——产品把这个包当作外部世界的
输入，和真实产线导出的包没有区别。

```powershell
.\.venv\Scripts\python.exe -m harness.gazebo.cli --help
```

工位跑一次抓取节拍：RGB-D 采集 → 视觉算法算出法兰指令 → UR5e 执行 → 评估到位误差，
然后把这一拍的全部材料导出成包。判定采用到位误差，**不做物理附着、不做搬运、
不连接任何真实设备**。

这样分开的好处是：产品的验证信号来自物理世界，而不是产品自己写的断言。

## 支持的视觉任务

当前有确定性核算器的是**手眼位姿引导**这条链：物体在相机系的检测 → 基座系的期望 TCP →
法兰指令。核算器把系统声明的 `camera_to_base`、`pick_offset_from_part`、`tool0_to_tcp`
各按四种用法比对一遍，只报数字，不点名段、不下结论。

检测、识别、分割类的故障目前可以被读懂、作为定界依据，但还没有对应的核算器——
产品会说"这一段还没查"，而不是给一个没有依据的排除。

**诊断侧看不到标准答案。** 观察包的清单只清点公开证据；私有评分材料在未导出的路径里，
诊断工具面够不到。这保证了"定界正确"不是因为模型提前知道了答案。

## 结果怎么看

一个案件的状态就是它的账本，随时可以查：

**诊断链路** —— 八段各自的判定、引用的证据号和依据。留在「还没查」的段会写明为什么没法排除，
而不是为了让链路好看给一个没有依据的「已排除」。

**四道门的当前状态** —— 每道门要么通过，要么给出还差什么：

```json
{"diagnosis": {"passed": true, "reasons": []}, "source_visible": true}
```

**每一轮做了什么** —— 展开任意一轮，看到它请求了哪几件证据、宿主实际交付了哪几件、
哪次调用失败了以及为什么。模型自称检查过而没有调用的，不能作为证据引用。

**判定的三种口径不能互相冒充**：

| 口径 | 说明 |
|---|---|
| `REPLAY` | 在这次运行真实产生的输入上，改过的代码算出了链路本来想要的结果 |
| `EVIDENCE_RECHECK` | 改动应用**之后**新采集的证据显示工位恢复了 |
| `not_a_recheck` | 拿来复核的证据采集于应用时刻之前，不能用来说明改动的效果 |

## 评测指标

这套系统不靠自评打分，可核对的量是这些：

| 指标 | 含义 | 本次演示 |
|---|---|---|
| 定界准确性 | suspect 的那一段是否与最终修复的位置一致 | 一致（变换接口） |
| 定界残差 | 声明变换的四种用法中，归零的那一格 | `tool0_to_tcp` 逆用两次 = `0.000000` |
| 跨工件一致性 | 同一包内多个工件的指纹是否一致 | A、B 完全一致 |
| 证据引用率 | 判定引用的证据中，宿主真正交付过的比例 | 100%（未交付的会被丢弃） |
| 调用预算 | 一轮内的工具调用数 / 上限 20 | 第一轮 5，第二轮 4 |
| 复跑结果 | 隔离复跑后指令与意图的偏差 | 法兰 Z `0.253 → 0.183`，差值 = 2×35 mm |
| 现场对照 | 改动前后逐件任务判定 | A、B 均由失败转通过 |
| 未审批拦截 | 补丁在无人审批时能否生效 | 不能，审批门 `passed=False` |

## 使用限制

- **图片**：单张不超过 2400 万像素；按 EXIF 校正方向、缩放到最长边 1600 像素、清除元数据后
  再送入模型。**原图始终保留在案件中**。
- **一轮的工具调用**：上限 20 次；一次 `read_evidence` 最多批量读 8 件。
- **一个人类消息推进一轮**：一轮没结束时不接受下一句。
- **源码读取**：只读**绑定提交**下的那一份，不读工作区当前内容。
- **观察包**：读取时逐件校验 SHA-256，对不上就拒绝交付。
- **仓库匹配**：包声明的提交必须在所连仓库里存在，否则连接被拒绝。

加密、损坏、超大或无实质内容的文件会被明确拒绝，并说明原因。

## 数据、隐私与安全边界

**凭据保护**
- 模型密钥只从服务端环境读取，不会出现在代码执行环境、日志文件、源码或接口请求里。
- 真实 `.env` 不会进入版本库。

**代码执行安全**
- 候选改动在一个 `git worktree --detach` 出来的独立工作树里复跑，跑完删除。**你的检出不动、
  当前分支不动、未提交的活不受影响。**
- 复跑执行的是**项目自己声明的命令**，产品不替项目决定怎么跑。
- 审批通过后补丁才写进仓库，写的是被冻结哈希认证过的那份字节，不需要人手抄。
- 合入主线与部署到工位不由产品执行。

**数据使用**
- 你上传的附件内容会作为诊断材料发送给你配置的模型服务。**请不要上传包含密钥、口令或商业
  机密的文件。**
- 图片在送入模型前会清除元数据（包括位置信息）。
- 所有数据存放在本地，不上传到 VisionDoctor 的任何服务器——本项目不运营任何云端服务。

**责任边界**
- 系统只在仿真环境中运行，**不控制任何真实机器人、控制器或产线相机**。
- 诊断结论和修复建议是辅助参考，**不替代工程师的专业判断和企业安全生产规范**。
- 是否采纳、是否上线，最终由人决定；系统永远不会自动合并代码。

## 能力边界

我们把能做和不能做的说清楚，避免踩坑：

**能做**
- 从一次运行的观察证据包出发，对视觉链路做八段定界，每段判定都挂着宿主真正交付过的证据。
- 用系统自己声明的变换做核算，**单次观察**就能区分「标定漂移」和「变换用错方向」，
  不需要 A/B 对照版本。
- 让模型在钉定提交上读源码、产出候选补丁，宿主算 diff 并在独立工作树里用这一包自己的输入复跑。
- 冻结补丁、人工审批、写入仓库、现场复核，全程留账。
- 上下文跨轮累积，案件跨重启存活。

**暂时不能做**
- 变换链核算目前覆盖手眼位姿这条链（`camera_to_base` / `pick_offset_from_part` /
  `tool0_to_tcp`）。检测、识别、分割类故障可以被读懂和作为定界依据，但还没有对应的确定性核算器。
- 复跑要求项目能用一条命令、通过文件交换 JSON 跑一次。不满足的项目仍可定界与产出补丁，
  但拿不到隔离复跑结论。
- 不宣称"任意视觉项目、任意未知故障都能自动修好"。

**怎么扩展**

| 想扩展什么 | 需要做什么 |
|---|---|
| 加一类故障的确定性核算 | 写一个只报数字、不点名段、不下结论的核算器，挂进工具面 |
| 换一个工位 / 场景 | 导出符合观察包契约的目录即可，产品不关心它来自仿真还是真实产线 |
| 加一段诊断链路 | 在链路定义里加段与职责范围，判定与门控逻辑不动 |
| 接入真实产线 | 按包契约导出，附 `sha256`、采集时刻与时钟域 |

**明确的前提**
- 模型没配置、材料校验不过、仓库与包对不上、门没过——系统都会直接说哪里不对，
  **不会**退化成一个凭规则猜测的结果。宁可明确失败，也不给你一个假装成功的结论。

## 示例工程

有两套，用途不同。

**`harness/gazebo/` 的演示工位**（当前主线）——生成一个被诊断项目并跑一次真实抓取节拍，
导出观察证据包。故障是工具补偿的逆变换被重复施加，TCP 稳定停在工件上方约 70 mm，
而这个偏差**在算法自己的输出里看不出任何异常**。见
[`harness/gazebo/README.md`](harness/gazebo/README.md)。

**`example/robot_cell_vision.bundle`**（初赛版本，10 KB）——一个可运行的 RGB-D 定位项目，
埋着相机外参被写反的回归，机械臂偏离目标 909.99 毫米，而它自带的 4 个单元测试全部通过
（测试全用单位矩阵，`inv(I) == I` 掩盖了正反向混用）。一条命令还原成带完整历史的真仓库：

```bash
git clone example/robot_cell_vision.bundle robot_cell_vision
```

详见 [`example/README.md`](example/README.md)。

## 接口调用

如果你想把 VisionDoctor 接进自己的系统，服务启动后访问 **http://127.0.0.1:8000/docs**
查看完整接口文档。常用接口：

| 用途 | 接口 |
|---|---|
| 创建 / 列出案件 | `POST` `GET /api/v1/cases` |
| 查看一个案件的全部状态 | `GET /api/v1/cases/{id}` |
| 接入观察证据包 | `POST /api/v1/cases/{id}/observations` |
| 直接交上来的图片与日志 | `POST /api/v1/cases/{id}/attachments` |
| 取回一份交上来的材料 | `GET /api/v1/cases/{id}/evidence/{eid}` |
| 连接项目仓库 | `POST /api/v1/cases/{id}/project` |
| 推进一轮（立即返回，后台执行） | `POST /api/v1/cases/{id}/turns` |
| 审批一个候选补丁 | `POST /api/v1/cases/{id}/approvals` |
| 标记已应用到现场 | `POST /api/v1/cases/{id}/applied` |
| 现场复核 | `POST /api/v1/cases/{id}/recheck` |
| 服务状态 | `GET /health` |

`GET /api/v1/cases/{id}` 一次返回案件的全部账本：`chain`（八段判定）、`hypotheses`、
`evidence`（含 `examined` 标记）、`gates`、`plans`（含冻结哈希与落地 commit）、
`turns`（每次工具调用的请求、交付与失败原因）、`recheck`。
`docs/运行证据/_raw/case_CASE-001.json` 就是这个接口的原始返回。

推进一轮是**非阻塞**的：`POST /turns` 立刻返回 `{"started": true}`，随后轮询
`GET /api/v1/cases/{id}` 的 `running.calls` 就能看到工具调用逐条落地。

## 常见问题

**必须装 Docker 吗？**
不必。诊断与复跑都不用容器——候选改动在一个 `git worktree --detach` 出来的独立工作树里跑，
跑完删掉。只有构建仿真工位镜像时才需要 Docker，而复现诊断本身不需要跑仿真。

**会自动改我的代码吗？**
诊断和复跑全程不动你的仓库。**只有你批准某个补丁之后**，那份被冻结哈希认证过的字节才会被
提交进去——这是为了避免手抄 diff 时混入没人审过的字符。合入主线和部署到工位仍然由你做。

**我需要先标出哪个版本是好的吗？**
不需要，也不需要 A/B 对照。变换链核算把系统声明的每个变换按四种用法各算一遍，
哪一格残差归零就是运行代码实际做的事——单次观察就能定形态。

**一定要有真实机器人或相机吗？**
不需要。`harness/gazebo/` 的仿真工位可以导出符合契约的观察包，产品不关心包来自哪里。

**为什么图片和文字用了两个模型？**
文字对话使用你配置的对话模型，图片分析使用本地视觉模型。两者分工明确，图片不会被降级成
"根据文件名猜测"这类无效处理。

**服务重启后会丢数据吗？**
不会。案件持久化在 `.runtime/vd-cases/`，证据账、链路判定、假设、补丁、审批和跨轮上下文
都会读回来。唯一不恢复的是重启时正在进行的那一轮——它的线程已经没了，显示成还在跑就是骗人。

## 开源协议

本项目以 [Apache License 2.0](LICENSE) 开放。开源依赖及其版本约束见
[`pyproject.toml`](pyproject.toml)，各依赖的许可证以其自身声明为准。

外部服务与模型披露：

| 用途 | 服务 / 模型 | 性质 | 可替代性 |
|---|---|---|---|
| 对话、定界、补丁生成 | 任一 OpenAI 兼容模型服务 | 按量计费的商业 API，或自托管开源模型 | 只依赖协议，不依赖任何服务商私有能力；换服务商只改 base URL 与模型标识 |
| 图片观察 | 同一接口 | 同上 | 可指向本机推理端点，让图片不出本机 |
| 仿真工位 | ROS 2 Jazzy / Gazebo / MoveIt 2 | 开源 | 只用于产出观察包；换成真实产线导出同样契约的包即可，产品侧不改 |
| 候选代码执行 | Git worktree + 子进程 | 开源 | 不需要 Docker；执行的是项目自己声明的命令 |

模型密钥仅从服务端环境变量读取，不写入日志、请求留痕或复跑环境。复跑子进程的环境变量
是白名单构造的，不继承密钥。
