# VisionDoctor —— 多模态机器视觉软件诊断与修复智能体

> 让机器视觉工程师用一次持续会话，把**现象、代码和现场**连接成可审计的诊断、修复与验证闭环。

从 3C 装配到汽车焊装、从锂电极片到药品包装，视觉系统承担着定位引导、缺陷检测、字符识别、
装配校验与分拣计数——它是产线的眼睛。一旦视觉软件算错，错误会立刻变成物理动作：抓偏、装错、
误判、停线；而定位一个视觉软件故障所花的时间，往往远超修复它本身。

机器视觉产线出问题时，工程师通常要在截图、日志、代码仓库和现场设备之间来回切换，凭经验定位
根因，再手动改代码、重新跑一遍验证。VisionDoctor 把这条链路收进一个会话：你描述现象、把图片
和日志直接发进来、连上项目仓库，系统会自己复现问题、定位根因、写出修改建议，并在隔离环境里
用可量化的指标验证效果，最后把结论交给你审批。

**代码改不改、上不上线，始终由你决定。VisionDoctor 从不自动合并任何变更。**

## 适合谁使用

- **机器视觉 / 机器人视觉工程师**：位姿估计漂了、检测框错了、识别结果不对，需要快速定位是哪次
  代码改动引入的问题。
- **产线软件维护人员**：现场只有截图、报警日志和一个跑不通的版本，需要一份有依据、可复查的
  排查结论。
- **设备与工艺工程师**：需要先判断到底是软件问题，还是机械、标定或来料的问题。
- **视觉算法团队负责人**：希望每一次修复都留下可追溯的证据链，而不是口头结论。

### 它面向哪一类故障

视觉软件的故障形态跨行业、跨任务反复出现，共性是**都发生在"成像看起来正常"之后**，因此大多
躲得过常规单元测试：

| 故障类型 | 常见形态 |
|---|---|
| **坐标与标定** | 手眼外参失效或方向写反；单位、轴向、四元数顺序混淆；工具 TCP 偏移与基准系变更 |
| **检测与识别** | 阈值漂移导致漏检误检；类别混淆与小目标丢失；后处理顺序变更改变结果 |
| **数据链路** | 时间戳错位、帧与位姿不同步；坐标系约定两端不一致；预处理或通道顺序被改动 |
| **配置与换型** | 换型后参数未同步；多工位配置串用；标定文件版本与代码版本错配 |

这类问题真正难的地方不在"看不见"，而在**看见了也说不清是哪一行代码**：现场信号高度分散
（截图在手机、日志在工控机、代码在仓库），常规测试用理想数据构造、覆盖不到真实配置，
结论多为口头传递、换个人就要从头再来。

典型场景（本仓库的[示例工程](#示例工程)正是这一例）：某次提交之后，机械臂抓取位置偏了约
0.9 米，而项目自带的单元测试全部通过。你把现场照片和日志发进会话，连上仓库，VisionDoctor
复现问题、找到坐标变换写反的那一行、给出修改并补上回归测试，在仿真里重新验证，误差回到
毫米级。

## 多模态输入

VisionDoctor 的诊断证据不只是文字，你可以在同一个会话里持续补充多种材料，系统会逐个真正分析
而不是仅仅存档：

| 输入类型 | 支持格式 | 系统会做什么 |
|---|---|---|
| **现场图片** | PNG、JPEG、WebP | 由视觉模型逐张分析，给出可见观察、诊断相关性、局限和置信度 |
| **日志与文本** | TXT、LOG | 提取内容并结合上下文分析异常线索 |
| **结构化数据** | JSON | 解析后分析字段与数值异常 |
| **文档** | PDF | 提取可检索文本参与分析 |
| **打包材料** | ZIP | 在内存中检查，提取其中的文本、代码、配置和日志 |
| **深度相机数据** | RGB + 深度 + 相机内参 | 参与位姿复现与几何验证 |
| **仿真现场** | Gazebo 采集的场景 | 一键附加到当前会话作为可复现证据 |
| **项目代码** | 任意结构的 Git 仓库 | 自动识别组件、资产、运行方式与验证方式 |

图片和附件的分析结论会在工作台上以「从图片中观察到」「从附件中分析到」卡片呈现，注明依据和
局限。**这些都是诊断线索，不决定修复是否通过**——通过与否由独立的验证程序判定。

## 快速开始

### 环境准备

- Windows + PowerShell
- Python 3.11
- Docker Desktop（必需，候选修改只在隔离容器里运行，不会碰你的机器）
- Ollama（用于图片理解）

### 安装

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev,api,web]"
.\.venv\Scripts\visiondoctor.exe build-sandbox
```

### 配置模型

在项目根目录创建 `.env`（可参考 [`.env.example`](.env.example)），或直接设置环境变量：

```powershell
$env:VISIONDOCTOR_LLM_API_KEY = "<你的密钥>"
$env:VISIONDOCTOR_LLM_BASE_URL = "https://api.deepseek.com"
$env:VISIONDOCTOR_LLM_MODEL = "deepseek-v4-flash"
```

图片理解使用本地视觉模型，不需要额外密钥：

```powershell
winget install --id Ollama.Ollama --exact
ollama pull qwen3-vl:4b
```

```text
VISIONDOCTOR_VISION_BASE_URL=http://127.0.0.1:11434
VISIONDOCTOR_VISION_MODEL=qwen3-vl:4b
VISIONDOCTOR_VISION_TIMEOUT_S=300
```

开始之前先确认模型可用：

```powershell
.\.venv\Scripts\visiondoctor.exe model-check
```

### 启动

两个 PowerShell 窗口分别启动服务和工作台：

```powershell
# 窗口一：服务
.\.venv\Scripts\visiondoctor.exe serve --host 127.0.0.1 --port 8000

# 窗口二：工作台
.\.venv\Scripts\visiondoctor-web.exe
```

浏览器打开 **http://127.0.0.1:8501**。

## 一次完整的使用流程

1. **描述问题**：新建会话，用自己的话说明现象，例如"上周还好好的，这周抓取位置整体偏了"。
2. **补充材料**：随时上传现场照片、日志、配置文件、PDF 报告。可以分多轮持续补充，会话不会丢
   上下文。
3. **连接项目**：填入本地 Git 仓库文件夹路径即可。**不需要**你指出哪个版本是好的、哪个是坏的，
   也不需要准备任何协议文件或表单——系统自己判断对比范围。
4. **提供验证依据**：选择已有的测试数据文件夹，或用内置仿真现场采集一份场景。
5. **启动诊断**：点击开始即视为你确认了本次的验证方案和改动范围。系统会复现问题、阅读代码、
   给出修改、在隔离环境验证效果。
6. **查看结论**：工作台用日常语言展示进度——正在复现问题、正在阅读代码、正在尝试修复、正在
   检查效果。
7. **审批**：结果满意就批准，会生成一个待你合并的候选分支；不满意可以直接拒绝并说明理由，
   意见会回到同一个会话继续调查。

一个项目可以同时开多个诊断会话，历史结论和已确认的项目知识会被复用，不用每次从头解释。

## 工作台功能说明

| 页面 / 功能 | 说明 |
|---|---|
| **会话列表** | 所有诊断会话按项目归组，可随时回到任意历史会话继续 |
| **对话区** | 发送文字和附件，查看图片/附件的分析卡片 |
| **项目** | 展示系统对你项目的理解：有哪些组件、怎么运行、怎么验证 |
| **待确认问题** | 当标定文件、运行入口、测试入口等存在多个可能时，系统会问你，回答后才继续 |
| **仿真现场** | 打开 3D 窗口、让机器人走一遍、采集相机与距离 |
| **运行记录** | 每次诊断的进度、验证结果、失败原因和审批状态 |

关于「待确认问题」：系统不会在含糊的地方替你猜。你确认过的答案会在后续版本中继续有效，除非
你选择的那个对象已经不存在了——这种情况下会重新问你，而不是沿用过期结论。

如果你的项目结构比较特殊，可以在仓库根目录放一个可选的 `visiondoctor.yaml` 来直接说明组件边界、
运行入口和验证数据。里面写的每个路径都必须真实存在。

## 仿真现场（3D）

没有真实产线也可以完成完整验证。VisionDoctor 内置 ROS 2 + Gazebo + MoveIt 2 + UR5e 仿真环境：

```powershell
.\.venv\Scripts\visiondoctor.exe build-gazebo
.\.venv\Scripts\visiondoctor.exe gazebo-view
```

工作台的 **仿真现场** 页面提供同样的操作：

- `打开 3D 现场` —— 启动可见的仿真窗口（Gazebo 官方界面，不是网页动画）
- `让机器人走一遍` —— 执行一段固定的验证动作
- `采集相机与距离` —— 采集一份 RGB + 深度场景，一键附加到当前会话

机器人只执行固定路线：`起始位 → 观察位 → 验证位 → 起始位`。**不做抓取，不做自由运动，
不连接真实设备。**

## 支持的视觉任务

| 任务类型 | 你的项目输出什么 | 系统验证什么 |
|---|---|---|
| **RGB-D 位姿** | 物体在机器人基座下的位姿 | 平移误差、旋转误差、重投影误差，以及仿真中机械臂实际到位精度 |
| **目标检测** | 类别、边界框、置信度 | 类别匹配的 IoU、精确率、召回率（检测框顺序不影响结果） |
| **文字识别** | 识别出的文本 | 字符错误率、词错误率，可配置大小写与空格处理方式 |
| **语义分割** | 像素级类别掩码 | 各类别 IoU、像素准确率、边界精度 |

诊断时系统只能看到输入图像和现场证据，**看不到标准答案**。标准答案单独存放，仅在验证阶段
使用，每次校验都会核对完整性。这保证了"通过验证"不是因为模型提前知道了答案。

## 结果怎么看

每次运行结束会给出明确结论。失败时会指出责任归属，而不是笼统地说"失败了"：

| 结论 | 含义 | 你该做什么 |
|---|---|---|
| 通过，等待审批 | 修改有效，各项指标达标 | 查看改动内容，决定批准或拒绝 |
| 修改本身有问题 | 候选改动没有真正解决问题 | 系统会自动重新尝试，最多 3 次 |
| 验证未通过 | 指标未达到要求 | 同上，会带着具体差距重试 |
| 证据不足 | 提供的材料不足以支撑判断 | 补充图片、日志或测试数据 |
| 仿真环境不可用 | Gazebo / MoveIt 环境本身出了问题 | 系统会自动重试两次；仍失败则转人工技术复核，**不会**因此去乱改你的业务代码 |
| 系统内部错误 | 编排环节异常 | 查看运行记录中的错误信息 |

每一次尝试都会留下记录，包括做了什么、看了哪些文件、验证结果是多少。你可以事后完整复查。

## 使用限制

为了保证响应速度和结果质量，输入有明确上限：

- **图片**：单张不超过 2400 万像素；系统会自动按 EXIF 校正方向、缩放到最长边 1600 像素、
  清除元数据后再送入模型。**原图始终保留在会话中**。
- **附件文本**：单个文件最多提取 4 万字符，单轮最多 8 万字符，整个会话保留最近 10 万字符。
  超出部分会明确告诉你哪些内容没有被读取。
- **PDF**：只提取可检索文本，不识别扫描件、页面图形和精确排版。
- **ZIP**：只提取其中的文本、代码、配置和日志，二进制文件会被跳过。
- **代码改动**：默认最多修改 3 个文件、100 行。
- **仓库状态**：仓库必须干净。有未提交或未跟踪的内容时会提示你先处理，避免验证结论对不上
  实际代码。

加密、损坏、超大或无实质内容的文件会被明确拒绝，并说明原因。

## 数据、隐私与安全边界

**凭据保护**
- 模型密钥只从服务端环境读取，不会出现在代码执行环境、日志文件、源码或接口请求里。
- 真实 `.env` 不会进入版本库。

**代码执行安全**
- 所有候选改动只在隔离容器中执行：**无网络访问**、文件系统只读、非特权用户、受限 CPU 与内存、
  受限运行时长。
- 模型生成的代码**绝不会**直接在你的电脑上运行。

**数据使用**
- 你上传的附件内容会作为诊断材料发送给你配置的模型服务。**请不要上传包含密钥、口令或商业
  机密的文件。**
- 图片在送入模型前会清除元数据（包括位置信息）。
- 所有数据存放在本地，不上传到 VisionDoctor 的任何服务器——本项目不运营任何云端服务。

**责任边界**
- 系统只在仿真环境中运行，**不控制任何真实机器人、控制器或产线相机**。
- 诊断结论和修复建议是辅助参考，**不替代工程师的专业判断和企业安全生产规范**。
- 是否采纳、是否上线，最终由人决定；系统永远不会自动合并代码。

## 能力边界

我们把能做和不能做的说清楚，避免踩坑：

**能做**
- 读懂任意目录结构的 Git 项目，识别 Python、C++、ROS 2、Docker、OpenCV、ONNX Runtime、
  TensorRT、MoveIt、Gazebo 等常见视觉工程要素——不要求你的项目叫 `src/` 或 `config/`。
- 对 RGB-D 位姿、目标检测、文字识别、语义分割四类任务做量化验证。
- 多轮会话、多模态材料、跨会话复用项目知识。

**暂时不能做**
- **自动修复执行**目前支持符合 VisionDoctor Python 执行契约的项目：提供运行脚本和测试脚本，
  通过标准输入输出交换 JSON。ROS 2 / Gazebo / MoveIt 通过专用的 RGB-D 位姿适配支持。
- 其他运行时（如通用 C++ 工程）目前可以被读懂和作为诊断依据，但还不能自动执行修复验证。
- 不宣称"任意视觉项目、任意未知故障都能自动修好"。

**怎么扩展**

架构上把「做什么任务」和「怎么判定对错」抽成了两个扩展点，会话、项目理解、Agent 调度、
隔离执行与审批流程不随场景变化：

| 想扩展什么 | 需要做什么 |
|---|---|
| 加一类视觉任务 | 实现一个验证适配器：输出契约 + 指标 + 阈值 |
| 加一种运行时 | 实现一个执行适配器，调度层不动 |
| 换一个行业场景 | 替换任务与验证标准，会话与证据链沿用 |
| 接入真实产线数据 | 以数据集形式提供可对证的参考真值 |

**明确的前提**
- 没有配置模型、模型不可用、材料不合规、改动不合法或 Docker 没启动时，系统会直接告诉你哪里
  不对，**不会**退化成一个凭规则猜测的结果。宁可明确失败，也不给你一个假装成功的结论。

## 示例工程


VisionDoctor 生成并经人工批准的修复。详见 [`example/README.md`](example/README.md)。

## 常见问题

**必须装 Docker 吗？**
必须。这是安全设计的一部分——模型写出来的代码只允许在隔离容器里跑。

**会自动改我的代码吗？**
不会。所有改动都在临时工作区完成，你批准之后才会生成一个候选分支，合不合并仍然由你决定。

**我需要先标出哪个版本是好的吗？**
不需要。连上仓库即可，系统自己判断对比范围。

**一定要有真实机器人或相机吗？**
不需要。内置仿真现场可以提供完整的 RGB-D 数据和机械臂验证。

**同时能跑几个诊断？**
本地服务支持两个并发运行任务。

**为什么图片和文字用了两个模型？**
文字对话使用你配置的对话模型，图片分析使用本地视觉模型。两者分工明确，图片不会被降级成
"根据文件名猜测"这类无效处理。

**服务重启后会丢数据吗？**
不会。会话、项目、运行记录和审批状态都持久化在本地，重启后可以继续。

[`pyproject.toml`](pyproject.toml)，各依赖的许可证以其自身声明为准。

外部服务与模型披露：

| 用途 | 服务 / 模型 | 性质 | 可替代性 |
|---|---|---|---|
| 对话、诊断、补丁生成 | DeepSeek `deepseek-v4-flash` | 商业闭源 API，按量计费 | 通过标准 OpenAI 兼容协议接入，换服务商只需改 base URL 与模型标识，无供应商锁定 |
| 图片理解 | `qwen3-vl:4b` | 开源模型，本地 Ollama 推理 | 图片不出本机 |
| 仿真 | ROS 2 Jazzy / Gazebo / MoveIt 2 | 开源 | — |
| 候选代码执行 | Docker | 开源 | 无网络、只读文件系统、非特权用户的隔离容器 |

模型密钥仅从服务端环境变量读取，不写入日志、请求留痕或候选执行容器。
