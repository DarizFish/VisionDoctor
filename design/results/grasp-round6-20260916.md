# 第六轮：软件层与源码层分层诊断

状态：2026-09-16，实施、三组真实模型诊断、补丁落地与 Gazebo 现场复核已完成。
可选的诱导对照未执行。每组只运行一次，按案例记录，不换算为准确率。

## 为什么做这一轮

五轮实施后，绑定项目就能随时读源码，偏离了初赛"先定界、再看代码"的门。已有记录显示：
几何故障以外，源码主要被拿来"读代码即排除"；同一故障从未做过有源码与无源码的对照；
现场也常常只有发布产物。本轮把软件诊断分为软件层和源码层，门放在两层之间。
方向说明见 [图式诊断计划](../grasp-diagnosis.md#当前方向软件层与源码层2026-09-16)。

## 实现

- **证据分层**：证据带 `layer`（observation / software / source）。观察包由导出方声明，产品只读取；
  派生证据取来源中最深的一层，读源码和补丁复跑固定为 source。
- **宿主规则**：
  - 可疑和排除必须引用非源码证据。模型只引用源码时降为未查，其他入口直接拒绝。
  - 源码层入口：有源码接入；源码版本等于观察包记录的运行版本；承载软件的图节点已有引用
    软件层证据的可疑判断。满足后下一轮才提供源码工具；读源码必须给出指向已定位对象的假设。
  - 补丁只接受处理方式为 `source_patch`、指向已定位对象的假设。
- **软件层工具**：`compare_runs` 按内容对比两次运行的版本和软件层记录，标识和时间字段不参与比较；
  `replay_running_version` 复用隔离复跑，用记录输入重跑运行版本并逐项对比记录输出。
- **接入等级**：项目绑定增加"是否可读源码"。不可读时仍可复跑，用来模拟只有发布产物的现场。
- **系统图**：删除"运行代码与配方"节点及其两条边，现为 12 个节点、17 条连线；
  采集、感知、抓取策略、指令计算标记为承载软件的节点。
- **处理出口**：`configuration | handoff | source_patch | physical | more_evidence`。
- **工作台**：接入条与源码层状态、双线框标出软件节点、证据按层排序、结论标注依据层、
  "交开发方"假设渲染为交接说明。
- **harness**：导出时自动声明 layer；`declare_layers` 为旧导出包按同一规则补写清单，材料与摘要不变；
  `evaluate_grasp` 增加 `--access`、`--reference`、`--repair-turns`。

## 结果

原始记录位于 `.runtime/grasp-evaluation/` 下对应目录，含 `summary.json`、`case-view.json`、
`cases/CASE-001.json` 和 `ui-check.json`。

### 1. 几何故障 · 可复跑、不读源码（`round6-runnable-geometry-20260916`）

201.6 秒、18 次工具调用、1 轮。没有任何源码调用，结束时源码层原因为"本案没有源码接入"。

- **定位**：指令计算与接口判为可疑，依据是按内容对比（相同输入、相同配置下 z 多 0.07 m）
  和两次变换链核算，均为软件层证据。感知、工具配置、采集对应按运行记录排除，
  标定记为未查，并注明未验证物理正确性。
- **出口**：H1 为交开发方；下一步列出失败运行的输入与输出、正常参考运行和运行版本。
- **评价：定位正确，部分正确。**
  - 提供了运行版本复跑，但模型没有调用，只把它写进下一项检查。
  - "工具变换被应用了两次"是从 0.07 = 2 × 0.035 推出的机制说法，没有源码佐证；只作为假设陈述，不算已证实。
  - 感知的排除依据是两次输入相同，范围写得准确，但措辞"工件检测正常"偏强。

### 2. 几何故障 · 含源码（`round6-source-geometry-20260916`）

255.0 秒、26 次工具调用、3 轮。源码层状态：第 1 轮前关闭（软件层未定位），第 2、3 轮前开放。

- **第 1 轮（软件层）**：没有源码调用。指令计算与接口判为可疑，依据与第 1 组同类；感知按输入相同排除。
- **第 2 轮（源码层）**：为 H1 读 `pick_demo/pipeline.py`，为 H3 读 `pick_demo/geometry.py`，
  随后为 H3 提交补丁。补丁只把三次逆工具补偿改回一次：

  ```diff
  -    compensated = compose(desired_tcp_in_base, inverse(tool0_to_tcp))
  -    overcompensated = compose(compensated, inverse(tool0_to_tcp))
  -    return compose(overcompensated, inverse(tool0_to_tcp))
  +    return compose(desired_tcp_in_base, inverse(tool0_to_tcp))
  ```

  隔离复跑时项目测试 1 项通过；A/B 指令 z 相对记录输出各降 0.07 m。
- **第 3 轮**：又读了两个文件，没有产生新结论。
- **落地与现场复核**：
  - 由 Claude Code 按用户批准的第六轮计划批准，只落地到专用副本
    `.runtime/gazebo-pick-cell/projects/repair-evaluation-20260916`（分支 `codex/two-layer-repair-evaluation`，
    提交 `848535f70c1e26206e0b9190f2e6cab2dda0a24d`）。不是新的人工点击审批。
  - 之后在 Gazebo 实跑 `run-20260916T095525Z-7fd260e0`：A/B 到位误差 2.199 mm / 2.062 mm，均在容差内。
    复核结果 `site_recovered`，运行来源和工件集合一致。
- **评价：根因、补丁和现场复核正确；报告有错误。**
  - 第 1 轮 H2 把"配置文件哈希不同"当成可能的配置差异，而 `compare_runs` 已给出内容相同。
  - 机制算式写成"高出 0.07 m（3 × 0.035 m）"；三次逆补偿相对正确值多出的是两次，即 0.07 m。
  - 第 2 轮下一步写"可部署到生产环境"，越过了审批和现场复核；第 3 轮措辞才收回。
  - 第 1 轮就把 H3 标为源码补丁，当时还没读源码。
  - 第 3 轮的两次读源码是无效调用。

### 3. 目标深度缺失 · 含源码（`round6-source-depth-20260916`）

283.3 秒、20 次工具调用、2 轮。源码层在两轮开始前都是关闭的，第 2 轮提交后才满足条件；本组没有源码调用。

- **定位**：采集交接判为可疑。依据：传感器原始深度的目标区域有效比例为 1.0，程序实际使用的深度只有 0.142；
  全图有效比例几乎不变；正常运行同一区域为 1.0；版本与配置相同。
- **排除**：感知拒绝输出判为正确行为，依据是算法输入里目标深度有效比例 0、阈值 0.6，属软件层证据；
  标定按配置相同排除；机器人正确跳过运动。
- **机制**：配准偏移或滤波清零保留为待证假设，第 2 轮出口为交开发方。没有把机制说成定论，
  但这是新实现上的单次运行，不能据此说第四轮的过度归因已被解决。
- **评价：定位正确，部分正确。**
  - "非确定性地清除"没有依据，只有一次故障运行和一次正常运行。
  - 第 1 轮对同一对象 `acquisition` 先后给了可疑和排除，宿主静默保留了后一条，
    导致源码层晚一轮才满足条件。这是宿主缺陷，本轮已修正（见下）。
  - 下一步建议用运行版本复跑来复现深度处理，但该工具复跑的是指令程序，并不覆盖深度管线。

## 规则执行核对

- **可读性控制**：第 1 组没有任何源码调用；第 2 组第 1 轮没有源码调用，之后每次读源码都带有假设编号。
- **非源码证据**：三组所有可疑和排除判断都引用了非源码证据。第 2 组"指令计算与接口"的
  可疑判断在第 2、3 轮同时引用了源码与运行记录；宿主降级没有被触发。
- **工具使用**：三组都调用了 `compare_runs`；都没有调用 `replay_running_version`。
