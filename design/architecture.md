## 1. 要解决的问题

机器视觉故障通常不是单一文件或单张图片的问题。一次任务失败时，现场可见的是抓偏、漏检或节拍
异常；真正的偏离可能发生在光学成像、采集时序、视觉算法、标定/坐标变换，或机器人消费视觉结果
之后。截图、日志、代码和轨迹分别存在时，工程师很难可靠地回答“哪一段最先偏离”。

**架构决策：** 产品以一次诊断案件（Case）为中心，接收带时间线和来源的多模态证据；先沿诊断
链路定界，再决定能否进行软件修复。代码修复是诊断后的一个分支，不是产品的入口假设。

这也限定了产品边界：它诊断机器视觉系统，视觉引导机器人是重要但可选的场景。若证据指向机器人
机械、控制器或其他非视觉内部故障，产品给出可审计的定界与转介，不假装修复该故障。

## 2. 最小领域模型

```text
人工描述 / 项目仓库 / 只读环境接口
                 │
                 ▼
       ObservationBundle（一次观察时间窗）
                 │  含原始工件、清单、时钟与版本信息
                 ▼
Case ── Evidence ── DiagnosticChain ── SegmentFinding / Hypothesis
                                             │
                ┌────────────────────────────┼───────────────────────────┐
                ▼                            ▼                           ▼
          软件/版本化配置                 外部物理动作                 非视觉边界
        候选改动 + REPLAY              HumanActionTask              转介 / 未决
                │                            │
                └─────────────── 人工审批、应用、EVIDENCE_RECHECK ────────┘
```

| 对象 | 职责 | 不能承担的职责 |
| --- | --- | --- |
| `Case` | 一次诊断的状态、参与者可见时间线、审批与关单 | 不存储或猜测评测真值 |
| `Evidence` | 不可变工件及其来源、哈希、时间、作用域 | 不能仅凭摘要升级为根因结论 |
| `ObservationBundle` | 一次有界观察的目录和时间关系 | 不是新的“案件根实体”，也不是旧 `Episode` 模型 |
| `DiagnosticChain` | 为定界提供共享、可寻址的系统段 | 不是固定排查顺序，也不等同于项目目录树 |
| `SegmentFinding` / `Hypothesis` | 记录已排除、可疑与待区分的解释，并引用 Evidence | 无证据时不得确认根因 |
| `HumanActionTask` | 表达必须由人或部署通道执行的外部动作和预期回证 | 不直接控制相机、机器人、PLC 或产线 |

## 3. 多模态证据与时间线

一个 `ObservationBundle` 表示“在一个明确时间窗内观察到的一次完整任务节拍”，也可以是用户上传的
离线录制包。它必须先有清单，Agent 再读取或请求其中的材料；不能把不带来源的大文件直接当作结论。

| 证据层 | 最小内容 | 对定界的价值 |
| --- | --- | --- |
| 任务结果 | 成功/失败、节拍、工位/配方、可用的外部结果信号 | 定义真正需要解释的症状 |
| 视觉现场 | 原始视频、关键帧、RGB-D、相机内参、曝光/触发状态 | 区分成像异常与下游异常 |
| 算法输入输出 | 输入帧、预处理结果、中间 mask/检测框/特征、最终输出与置信度 | 找到视觉算法内的首次偏离 |
| 软件运行 | 结构化日志、异常、延迟、进程/模型/容器/代码版本 | 将行为绑定到可复现的软件版本 |
| 标定与交接 | 内外参、变换树、单位约定、时间同步质量 | 区分标定、坐标和时序问题 |
| 机器人（可选） | 指令与实际轨迹、关节状态、TCP、夹爪、视觉结果消费时间 | 判定问题是否越过视觉—执行交接边界 |
| 人工上下文 | 现象、换型/维护记录、近期改动 | 提出假设，但不替代可核证证据 |
| 历史对照 | 正常节拍、已验证项目回放、历史案例 | 作为普通 Evidence 对照，不向 Agent 提供隐藏真值 |

### 3.1 时间一致性是不变量

每个工件至少记录来源、采集时间、所属时钟域、序号和完整性哈希。跨源比较还必须记录对齐方式及其
误差；没有共同时间基准或误差超出声明范围时，系统只能报告“无法据此做跨源归因”。

例如，视觉输出正确但机器人抓偏，可能是外参反向、帧与位姿错配，或机器人内部故障。缺少视觉输出
时间、变换发布时间和机器人消费时刻时，三种解释均不能被排除。

原始视频和完整日志保存为 Evidence；提供给模型的是按时间索引的关键帧、曲线、结构化摘要和按需
展开的片段。这样既保留审计能力，也避免将无界原始数据塞入模型上下文。

## 4. 只读环境接口

环境接口负责把现场或演示环境中的观测转换为 `ObservationBundle`。它是**采集边界**，不是控制器，
也不是诊断 Agent 的工具箱。

```text
Agent → CollectionRequest（所需证据、时间窗、上限）
人/调度器 → 授权采集
EnvironmentAdapter → 只读观察 → ObservationBundle + manifest
Product → 验证清单、保存 Evidence、开始诊断
```

`CollectionRequest` 可请求一个既有时间窗，或订阅“下一次已发生的完整节拍”。它不能要求“让机器人
运行一次”“修改曝光”“重标定”或执行任意 shell 命令；这些都是外部副作用，必须走人工/部署通道。

适配器的最小接口为：

- `discover_capabilities()`：声明可读来源、最大时间窗、格式、时间精度和数据上限；
- `collect(request)`：在被授权的范围内读取并产出清单与工件；
- `read_artifact(bundle_id, artifact_id)`：按已登记的 ID 读取工件，不接受任意路径；
- `health()`：报告连接、权限、时钟与采集失败，不伪造空证据。

适配器不得暴露故障注入开关、评测真值、任意环境命令、写权限或模拟器专有语义。它可以由 Gazebo、
ROS bag、日志平台、文件夹或未来现场系统实现，但产品核心不以 `simulation` / `gazebo` 类型分支。

## 5. 诊断链路与硬门

默认链路为：

```text
工件/来料 → 光学成像 → 采集与时间链路 → 视觉算法 → 任务结果
```

当证据显示视觉输出被执行机构在坐标系中消费时，一起扩展三段：

```text
标定配置 → 变换接口 → 机器人侧
```

每段只可标记为“未测”“已排除”或“可疑”；后两者必须引用 Evidence。确诊前，Agent 可以提出多个
假设并请求能区分它们的新证据。每条用户消息至多推动一个 `DecisionTurn`，由宿主记录真实工具调用
和产物，不能把“模型声称已检查”当作审计记录。

进入修复和关闭需要四道硬门：

1. **诊断门**：至少一个可疑段、已排除段和根因假设均有证据绑定，且结论不越过证据作用域。
2. **审批门**：软件候选或动作计划冻结为可审查对象；未经人工批准不得应用。
3. **外部动作门**：重标定、调光、机械调整和部署等动作必须有类型化工单，以及预先命名的回传证据。
4. **现场复核门**：隔离环境通过只能证明技术回归；“现场恢复”只能由应用后的新
   `EVIDENCE_RECHECK` 证据授予。

产品侧只有 `REPLAY`（应用前的隔离复现/项目命令/回归）和 `EVIDENCE_RECHECK`（应用后的新证据
复核）。项目自身碰巧使用仿真时，它仍只是普通可运行项目命令；不能获得特殊的“仿真验证档位”。

## 6. 复赛演示：独立 Gazebo 抓取场景

**决策：** 演示环境、故障注入和外部评分放入 `harness/`，而不是产品包。`harness/` 可以调用产品
公开接口；产品不得 import `harness/`，也不得读取故障真值。

演示场景必须独立运行，至少包含：

- 机械臂、受支持的末端夹爪、工作台和可识别工件；
- 固定 RGB-D 相机以及相机—机器人变换；
- 可运行的视觉/算法项目：有明确输入、输出、结构化日志、版本化标定配置和测试入口；
- 一次可观察的抓取节拍：取图、算法计算、发布/消费目标、轨迹执行、抓取/放置结果；
- 只读 Gazebo 环境适配器，采集视频/关键帧、深度、相机信息、算法 I/O、日志、变换、轨迹和任务结果；
- 一个明确的软件回归，例如 `T_base_camera` 被错误求逆。故障版本应稳定抓偏，而项目原有的弱单元测试
  可以仍然通过；修复后同一场景恢复到预先声明的容差内。

演示应可展示以下两次独立运行：

1. 故障版本运行，环境接口生成完整 `ObservationBundle`；Agent 只能看到该包和项目材料。
2. Agent 在隔离 worktree 形成候选修复并通过 `REPLAY`；人工批准/部署后，演示环境运行修复版本，
   接口生成新的证据包，产品以 `EVIDENCE_RECHECK` 报告恢复范围。

故障位置、预期修复和评分阈值仅属于 `harness/`。它们可以用于演示/评测判分，不能进入 Agent 提示、
产品 Case、公开时间线或环境接口返回值。

## 7. 明确不做的事

- 不把一次节拍抽象成旧架构的 `Episode`，也不迁移 `DiagnosisCase` 工作台。
- 不让 Agent 直接操纵机器人、PLC、相机、灯光或标定。
- 不因演示使用 Gazebo 而让产品把“仿真通过”表述为“现场恢复”。
- 不要求真实项目已有仿真；没有自动采集接口时，人工上传同格式证据包仍可工作。
- 不在首个切片重写整个 UI、模型提供商或原有隔离执行器。

## 8. 架构验收判据

- 从文件型和 Gazebo 型采集端得到的包都通过同一 `ObservationBundle` 校验，产品核心不出现
  `gazebo` / `simulation` 分支。
- 任一跨源结论可回溯到带时间、哈希和来源的 Evidence；时间质量不足时系统拒绝跨源归因。
- 故障抓取演示能独立重现“坏版本失败—软件修复—修复版本通过”，且产品从未获得故障真值。
- 非软件根因只能产生人工动作或转介，不能生成代码补丁。
- 无审批不得应用；无新回传证据不得宣称现场恢复。
