# 抓取场景的图式诊断计划

状态：2026-09-16，结构诊断已实施，实测见第七轮记录；软件层/源码层两层诊断已实施，实测见第六轮记录；2026-09-12 既有五轮比赛 Demo 实施及验收完成；系统接入、理解与建模仍为下一阶段规划。误判与能力边界见 [PROGRESS.md](PROGRESS.md)。
这是用户确认的新方向；与 2026-09-02 的链式设计冲突时，以本文为准。
可独立阅读的快照：[当前架构快照](grasp-architecture-20260917.md)、[方案快照](grasp-plan-20260917.md)。

## 目标与范围

在固定抓取工位上，通过多个代表性故障验证 Agent 的诊断、软件修复、人工处理建议和继续取证能力。
按用户 2026-09-12 最新范围，当前聚焦视觉采集、识别定位、目标计算/规划与机器人到位，
故障不限于坐标变换；不扩展接触、夹持及其物理验证。既有完整抓取知识保留为背景，
知识范围广于当前建设和实测范围，不因此产生扩展接触、夹持的任务。

已确认原则：比赛核心优先；场景固定抓取但不限定故障；方案可以领先 Demo；追求准确和可信，
接受误诊与未知；不考虑兼容性；可按需改造仿真；每轮完成后自审。工程实施约束见根目录 AGENTS.md。

## 当前方向：软件层与源码层（2026-09-16）

五轮实施后，诊断可以随时读源码。这偏离了初赛"先定界、再看代码"的门，并带来三个问题：
现场常常只有发布产物；源码注释和命名会诱导模型；实测中源码多被用来"读代码即排除"。
现在把软件诊断分成两层，门放在两层之间。

| | 软件层（运行起来的程序） | 源码层（实现代码） |
|---|---|---|
| 证据 | 运行版本、实际加载的配置、模块输入输出、日志、记录版本复跑，及其计算 | 与运行版本一致的源码、补丁复跑 |
| 能下的结论 | 模块输出违反约定；配置或版本与正常运行不同；输入超出模块声明的适用条件 | 已定位异常由哪段实现造成 |
| 出口 | 改配置、带复现输入交开发方、现场处理、补证据 | 源码补丁 → 隔离复跑 → 审批 → 现场复核 |
| 没有源码时 | 完整可用 | 不可用，结论停在软件层 |

宿主强制三条规则：

1. **可疑和排除必须引用非源码证据。** 只引用源码的判断降为未查。
2. **源码层入口**：有源码接入；源码版本等于观察包记录的运行版本；某个承载软件的图节点已有
   引用软件层证据的可疑判断。满足后，下一轮才提供源码工具，读源码必须对应一个已提交假设。
3. **补丁**只接受处理方式为"源码补丁"、指向已定位对象的假设。审批门与现场复核门不变。

证据层由观察包导出方声明，产品只读取。承载软件的节点为采集、感知、抓取策略、指令计算，
以及流入它们的交接。"只有发布产物"在 Demo 中以"可复跑、不可读码"的接入方式模拟。
实施与实测见 [第六轮记录](results/grasp-round6-20260916.md)。

## 当前方向：结构诊断（2026-09-16）

两层诊断之后，"哪里坏了、哪里排除、哪些还分不开"仍是模型读测量后的判断。
本方向让 LLM 继续主导调查，但把这部分事实交给宿主计算：**LLM 主导调查，不主导事实。**

| 部分 | 谁做 | 内容 |
|---|---|---|
| 诊断模板 | 人工整理，挂在系统图上 | 方程（含哪些变量）、变量、测量（哪类记录提供哪个变量）、故障挂接（节点或节点的故障模式破坏哪些方程）、预实现检验 |
| 测量绑定 | LLM | 把本案记录对应到模板的测量；记录缺字段则不算测量 |
| 结构分析 | 宿主，通用引擎 | 关联矩阵、Dulmage–Mendelsohn 过约束部分、可检测、可隔离、可用检验、缺检验 / 缺测量、区分建议 |
| 残差检验 | 宿主，预先实现 | 只运行结构认可的检验，给出残差、阈值及来源 |
| 隔离 | 宿主 | 单故障、必然触发两条假设下的剩余候选、核算排除、未检验、不可检测 |

宿主强制两条规则：判定引用核算时不能说反话；核算排除的节点不能作为打开源码层的软件层定位。
不做 MSO 自动枚举、残差自动生成或自动建模。模板外的原因（遮挡、成像质量等）仍由 LLM 按证据取证。
与两层诊断的关系：隔离回答哪个节点坏了，测量工具回答怎么错，源码层回答哪段代码；核算结果属于软件层派生证据。
实施与实测见 [第七轮记录](results/grasp-round7-20260916.md)。

## 下一阶段：接入系统、理解系统、系统建模

### 已确认方向与规划状态

用户确认这三项是重要能力，需与诊断并列规划。既有 Demo 主要证明在预设参考模型和给定观察上
开展诊断；下一阶段关注 Agent 如何认识一个具体工位。本节记录方向与架构建议，
不表示已经具备通过现场视频或任意设备接入自动还原系统的能力。

| 能力 | 核心问题 | 预期产出 |
|---|---|---|
| 接入系统 | 可以从哪里观察现场？ | 可读信息源、可获取的数据、观察盲区 |
| 理解系统 | 设备、程序和数据分别意味着什么？ | 角色、功能、数据语义、运行规则和待确认关系 |
| 系统建模 | 如何组织这些理解以支持诊断？ | 当前工位的组成、依赖、约束及其依据 |
| 诊断系统 | 哪些原因能解释异常，如何区分？ | 候选解释、支持/反对证据、检查建议与结论 |

通用领域知识描述“视觉抓取通常如何工作”；现场系统理解描述“这个工位实际如何工作”。
先定义诊断所需的最小系统模型与必要证据，再选择接入方式。四项能力相互迭代：
诊断可以暴露观察缺口，补充接入可以修正系统理解，新证据可以更新模型或撤回判断。

### 规划中的信息来源

| 信息源 | 主要作用 | 解释边界 |
|---|---|---|
| 用户描述、流程图、工位资料 | 任务目标、正常行为、设备角色与近期变化 | 可能遗漏或与现场不一致 |
| 用户拍摄的视频 | 物理布局、动作顺序、工件变化、明显遮挡和偏移 | 不直接证明内部数据流、精确坐标或故障因果 |
| 相机图像、深度、采集信息 | 相机实际观察、目标区域质量、采集时间 | 与用户旁观视频区分；还需确定下游使用了哪一帧 |
| 工控机只读资料 | 程序配置、视觉输出、日志、数据交接和运行版本 | 接入成功不等于已知程序角色、当前配置及实际消费关系 |
| 机器人只读数据 | 指令目标、实际反馈、模式、报警及坐标/工具配置 | 到位符合指令不能证明上游目标正确 |
| 标定文件、手册、接口说明 | 数据语义、设备能力和正常约束 | 配置记录不能独立证明现场物理关系仍然有效 |

视频、内部运行数据与文档相互补充；关键关系保留来源与确认程度，允许局部未知。
只读接入用于观察，不包含自动运动或修改设备参数。不能假定任意工控机、相机、机器人
都已可连接或能提供完整证据；设备接入与建模效果需后续分别验证。

### 面向诊断的领域模型

建议以“面向诊断的视觉引导抓取系统模型”为骨架，将三类内容关联呈现：

| 模型视图 | 内容与职责 |
|---|---|
| 系统结构与依赖图 | 设备、功能、关键数据及坐标/单位/时序/任务约束，描述工位如何工作 |
| 运行证据图 | 某次采集、检测、计算、指令与反馈的对应关系，保留来源、时间和版本 |
| 故障假设图 | 候选原因、预测现象、支持/反对证据与下一项鉴别检查 |

领域知识提供正常关系与鉴别规则，现场资料填充工位实例，运行证据校正理解，故障假设组织诊断。
执行有先后顺序，诊断需表达交叉依赖和竞争解释；依赖关系不能直接当作本次故障的已证实因果。
人工整理的参考图、现场实例模型与自动因果学习能力分别说明，不混用完成声明。

### 比赛范围与下一步

规划建议采用固定工位、有限只读接入、辅助理解与建模、关键关系人工确认、运行证据诊断的组合。
无需扩展大量工业协议或追求完全自动建模；不扩展接触、夹持，也不引入企业规模化建设。
首个 [PICK-A17 最小工位实例模型](grasp-cell-model.md) 已按既有运行记录整理为文档草图，
包含功能依赖图、关系依据及观察缺口，尚未成为 Agent 自动建立或运行时加载的实例模型。
下一步据此确定首次接入所需的最小输入材料，并用一个有结构差异的实例检查框架复用性，再选择具体接入方式。
验证应检查模型关键关系是否符合现场、能否暴露缺口及支持诊断；仅生成图不证明理解正确。
当前仅完成方向记录与首个实例草图，不启动上述实现或新实验。

## 已完成阶段的五个方向

以下保留此前五轮实施依据；其中完整抓取知识与参考图的范围，不代表下一阶段要扩展接触、夹持。

1. **系统模型**：用任务依赖图表达工件、成像、采集、感知、抓取规划、指令、运动、接触和结果，
   以及标定、工具和软件配置的共同依赖。图是参考模型，不假装已自动发现现场设备。
2. **领域知识**：覆盖工件工艺、光学、时序、感知、几何、规划、执行接触、软件、测量与诊断。
   重点提供正常关系、竞争解释、鉴别方法和排除边界；知识本身不构成本案观测证据。
3. **诊断能力**：模型可在图的节点和连接处提出假设、引用观察，说明检查范围与缺口，选择下一项
   检查。只读项目资料用于诊断；候选执行与应用由宿主控制。增加证据时允许撤回早先判断。
4. **多故障验证**：保留原几何案例，并覆盖不同成因。测试包括软件、成像/感知、时间、外部物理
   原因，以及正常/证据不足对照。故障答案仅用于 harness 评分，不进入产品上下文。
5. **比赛表达**：展示系统图、真实工具和证据、竞争解释及处理出口。保留失败记录，分别说明已实现、
   已演示和后续设计能力，不用单次成功外推所有故障。

## 验收证据

| 要求 | 能证明它的证据 |
|---|---|
| 图参与诊断 | Agent 实际收到图、检查依赖/交接、将结论绑定节点或边；接口和工作台可查看 |
| 完整知识范围 | 可读取的领域条目覆盖上述知识；条目有正常规律、鉴别检查及结论局限 |
| 多模态诊断 | 图像、深度、结构化记录等经实际工具被检查并关联，报告量的来源与适用条件 |
| 多种故障 | 同一工位/任务不同成因的实际诊断记录，公开输入与私有答案分开 |
| 处理出口 | 软件候选复跑、人工处理建议、证据不足继续取证，各有可核实案例 |
| 效果与可信度 | 对照真实答案记录正确/错误/未知及错误动作；有有限重复运行，不要求全对 |
| 现场演示 | 至少重新跑通现有 Gazebo 主案例及有代表性的非坐标故障；保存运行证据 |
| 比赛材料 | 仓库内的当前方案和演示指引与证据一致，并列出方案与 Demo 的差距 |

此前验收仅验证到位，不把模型知识中的夹持/滑移能力写成已完成的物理演示。
按最新范围，接触、夹持及保持物理仿真不列入下一阶段任务。

## 实施顺序

- 第一轮：系统图、十类领域知识、Agent/API/工作台接入，以及基本行为验证。
- 第二轮：补齐有区分价值的多模态测量和竞争假设处理，核对现有主案例。
- 第三轮：改造 harness 形成不同故障来源与对照，进行真实模型和仿真实验。
- 第四轮：根据误诊修正知识或取证能力，整理比赛方案、演示证据与实际边界。

每轮以验证结果决定后续工作量。不能仅增加文档、图和提示词就声称诊断准确率提高。

| 比赛材料 | `grasp-competition.md`、`grasp-demo.md` 与五轮实验记录已同步实际结果，明确方案/实现/实测差距。已完成 |

完整测试 164 passed，Ruff 通过；主仓库无提交/推送。
这些证据不代表每个诊断正确，也不代表复杂工件或完整接触物理已经实现。
各验收项均有对应实现或实际行为记录；“处理建议已验证”只表示建议与观察缺口有关并可供现场执行，
不表示建议已被执行、每个具体根因都正确或物理恢复已成立。该边界与本计划接受误诊、未知及 Demo 差距一致。
