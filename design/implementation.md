## 0. 起点、目标与连续性

### 已核实的基准事实

| 事实 | 证据 | 对重构的影响 |
| --- | --- | --- |
| 基准已有持续会话、附件处理、项目理解、隔离 Git worktree、Docker 运行器和补丁范围策略 | `sessions.py`、`sandbox/`、`schemas/models.py` | 这些资产应优先复用，不从零重写 |
| 外部入口 `Incident` 强制要求好/坏提交、case set、QA reference 和验收阈值 | `schemas/models.py`、`docs/INCIDENT_FORMAT.md` | 这是受控修复合同，不适合作为真实诊断案件入口 |
| 产品内有 `SimulationService`、Gazebo API 和 `robot_backend` 分支 | `simulation.py`、`api/app.py` | 与“产品不识别仿真、演示归 harness”目标冲突，须迁移而非扩展 |
| 已有 RGB-D 场景、MoveIt 固定运动探针和带外参求逆缺陷的 `robot_cell_vision.bundle` | `ros/`、`example/` | 可作为抓取演示的起点，但现有资产没有被验证为完整抓取闭环 |

### 本轮目标

交付一个证据驱动的最小垂直切片：同一份一次节拍证据包可以来自人工上传、文件夹或 Gazebo 环境层；
系统以时间线和诊断链路定界；若根因是软件，才产生隔离候选修复并走 `REPLAY`。完整方案见
[architecture.md](architecture.md)。

本轮不以“迁移所有旧 API / UI”为目标。旧路径在迁移期可保留为基准演示，但新 Case 路径不得依赖它们。

## 1. 改动策略：保留、改造、停止扩展

| 范围 | 动作 | 原因 |
| --- | --- | --- |
| 附件摄取、图像观察、项目扫描 | 保留并接入 `Evidence` | 已能处理多种材料，改造成本低 |
| `GitWorktreeSandbox`、`DockerPythonRunner`、`PatchPolicyEvaluator` | 保留，作为软件候选的隔离执行底座 | 已具备候选隔离和修改范围约束 |
| `Incident` / `ReferenceSignal` | 从新产品入口移除，不要求立即删除 | 新 Case 不应要求事先知道好/坏提交或隐藏 QA 真值 |
| `SimulationService`、Gazebo 专用 API、`robot_backend` | 停止在产品中扩展，迁至 `harness/` | 演示/评测环境不应成为产品领域概念 |
| `DiagnosisCase`、`episodes/`、多角色盲测模型 | 不引入 | 它们属于已否决的旧方向，且会放大迁移范围 |
| 现有 Web 工作台 | 后置，仅增加 Case 所需最小展示 | 先证明证据定界和修复闭环，再做界面重构 |

## 2. 分阶段实施

### M1：可独立运行的 Gazebo 抓取演示（最高优先）

新增 `harness/gazebo/`，其中包含场景、启动脚本、演示项目、故障注入/判分和只读采集适配器。它不被
`src/visiondoctor/` import。

场景要求：UR5e、可视化双指夹爪、工作台、两个不同的可达工件工位、固定 RGB-D 与观察相机，以及一次
“识别 → 坐标换算 → 工具补偿 → 机械臂到抓取位 → 任务结果”的完整节拍。抓取采用到位判定，不提前
建设物理附着/搬运。首个软件回归固定为 TCP/工具补偿错误：故障 HEAD 将逆补偿重复应用，使 TCP 在向下
抓取时稳定停在工件上方。应保留实际算法输入/输出、结构化日志、代码提交、工具配置与标定文件哈希。

验收：人工运行故障版本可稳定得到抓偏/失败，修复版本在相同输入与容差下成功；两次运行都产出完整
证据包。故障真值只供 harness 判分，不能传给产品。

### M2：统一证据包与只读环境层

新增以下产品模块（具体命名可在实现时微调，但职责不得混合）：

```text
src/visiondoctor/
  evidence/                 # 不可变 Evidence 与工件存储
  environment/              # ObservationBundle、适配器协议、文件型适配器
  cases/                    # Case、时间线、案件服务
  diagnostic_chain/         # 链路、段结论、假设校验
```

第一种生产可用适配器是 `FileBundleAdapter`：读取预打包目录的 manifest 和工件。Gazebo 适配器由
`harness/` 实现同一协议并在集成演示中注入；产品不判断其来源环境。接口只能发现能力、读取有界时间窗
和读取已登记工件，不能启动机器人、写配置或执行任意命令。

验收：人工上传与两种适配器产出的包具有相同 schema；缺哈希、越界路径、无时间窗或时钟质量不足的包
被拒绝或降级为不可跨源归因。

### M3：Case 与诊断链路定界

将新入口从“提交完整 Incident”改为“创建 Case → 连接项目/证据 → 建立链路 → 调查”。现有 Session
可作为对话与附件存储实现暂时保留，但 Case 必须是新路径的状态根。

实现默认五段链路，并在发现视觉输出被执行机构消费时同时加入标定、变换、机器人三段。每个
`SegmentFinding` 与 `Hypothesis` 必须引用 Evidence；Agent 每次只提交一个可审计 `DecisionTurn`，
工具调用由宿主记录。

验收：在演示故障包中，系统能把成像和算法输出与“标定/变换接口可疑”区分开；若缺少时间对齐或关键
工件，只能生成证据请求，不得给出确诊或补丁。

### M4：软件修复与外部动作分流

将保留的隔离 worktree 能力接到新 Case：只对已通过诊断门的软件/版本化配置根因生成候选；候选在
隔离环境执行项目 `REPLAY`，受现有补丁策略限制。把重标定、调光、换件、部署等改为类型化
`HumanActionTask`，并在创建时声明预期回传证据。

验收：软件场景可完成“候选 → REPLAY → 审批 → 应用 → 新证据复核”；外参物理漂移等非软件场景不产生
代码补丁，只能等待人工动作回证；未审批或无回证均不能关单。

### M5：迁移 API、界面与旧仿真路径

增加 Case API 和最小 UI：证据清单/时间线、链路、当前假设、下一步采集请求、四道硬门和审批对象。
完成等价性测试后，移除产品的 `/simulation`、`robot_backend` 和 `SimulationService` 路径，将 ROS/Gazebo
资源及其运行命令收口到 `harness/`。README 与运行说明在此阶段更新，不提前宣称新能力已经可用。

## 3. 演示工程的具体改造

独立演示项目应以自身 Git bundle 分发正常提交与故障 HEAD，而不是由 VisionDoctor 生成的内部 Demo：

1. 补上可执行的抓取/放置任务、夹爪状态和任务成功判据；现有固定运动探针不足以证明抓取。
2. 在一次任务中记录原始/关键 RGB-D、相机信息、算法输入输出、变换、指令/实际轨迹、任务结果和
   结构化应用日志；所有条目与同一 `run_id`、时间窗和代码/配置版本关联。
3. 故障版本只改变 TCP/工具补偿的一个可解释软件点；正常版本与修复后候选使用同一场景和输入。
4. 由 harness 生成 `ObservationBundle`，产品通过环境层读取；产品永不读取“错误在哪一行”“期望
   位姿”“正确补丁”等判分材料。

建议第二个、后续再加的故障是“图像帧与机器人位姿时间偏移”，因为它能检验时间线是否真的参与定界；
首个场景只做工具补偿回归，避免同时改变标定和时间两个变量而无法归因。

## 4. 关键决策与取舍

### D1：一次节拍是证据包，不是新的案件模型

**决策：** 以 `ObservationBundle` 承载时间线和多模态工件，Case 仍是生命周期根。

**取舍：** 可避免引入旧 `Episode` 体系，同时允许一个 Case 有多次故障/正常/复核观察。代价是需要严格
维护 bundle、Evidence 和 Case 之间的引用关系。

**重新评估条件：** 若未来必须实时流式诊断且一个 Case 有百万级独立事件，再评估单独的事件存储；当前
复赛演示不需要因此提前建复杂平台。

### D2：环境层只读，动作一律显式分流

**决策：** 环境适配器只读取，不能触发机器人节拍或修改现场；需要动作时创建 HumanActionTask。

**取舍：** 自动化程度低于“Agent 直接控制 Gazebo/设备”，但责任和审计边界清晰，能迁移到真实现场。

**重新评估条件：** 若接入受认证的独立部署控制系统，可新增受控执行通道；它仍不能伪装成采集接口。

### D3：仿真属于 harness，不是产品验证档位

**决策：** Gazebo 可以是环境层的一个实现，但 `src/visiondoctor/` 不认识其身份，也不依赖它。

**取舍：** 产品无法把“仿真通过”包装为现场恢复；代价是需在 harness 做额外装配和演示脚本。

**重新评估条件：** 无；这条边界是产品可迁移性和评测真值隔离的前提。

### D4：名义核算器只报测量，不报结论

**决策：** 变换链核算器输出重算位姿与残差（正向复合残差、取逆复合残差、实测 TCP、任务偏差），
不点名可疑段，也不给出故障家族。

**取舍：** 定界与根因判断因此完全由模型承担，可被证伪；代价是模型可能读不懂数字而失败。反过来，
若核算器直接给出「interface 段不自洽」或「工具补偿方向用反了」，产品就已经握有答案，模型只是复述，
「沿链路定界」这项能力有一半是硬编码的，演示时无法声称是模型做到的。

同一组残差还要再判一次归属：方向约定被反用，可能是代码缺陷、配置写反或标定漂移——三个故障家族，
修复方式分别是改代码、改配置和派人重标定。这一层判断不可下沉到确定性代码。

**重新评估条件：** 若多轮实测表明模型稳定无法从残差得出方向结论，则先补的是「取逆后是否吻合」这类
仍属测量的中性字段，而不是直接给段位或结论。

### D5：定界失败先记录形态，不改提示词重试

**决策：** 第一次真实定界若不通过判据，记录调用了哪些工具、在哪一步偏离、引用的证据是否真被读取，
并对失败形态归类；不在同一轮内调整提示词重跑。

**取舍：** 出结果更慢，但避免把「改提示词—重跑—通过」当成能力提升。单场景单次运行没有可比基线，
分数摆动可能大于改动效应，那样得到的通过不可复现，也无法回答下一次还能不能通过。

**重新评估条件：** 建立多次采样基线后，可以按分布判断提示词改动是否真的带来改进。

## 5. 验证策略

常规自动化验证保持确定性：`pytest` 与 `ruff check .` 不依赖真实模型 API、Docker 或 Gazebo。为新路径
增加 FileBundleAdapter、Evidence 不变性、时间对齐拒绝、链路证据绑定、硬门和无产品仿真 import 的测试。

真实 Gazebo 抓取演示和真实模型诊断属于人工验收：必须实际运行故障与修复两次，并保存对应 bundle、
公开时间线和 harness 判分结果。环境不可用时记录为“未验证”，不能以单元测试代替。

## 6. 主要风险与下一步

| 项目 | 状态 | 缓解方式 |
| --- | --- | --- |
| 基准 ROS/Gazebo 资产是否含可用夹爪和真实抓取闭环 | 已验证为到位判定闭环 | M1 已完成真实 Gazebo/MoveIt 故障与正常 A/B 人工验收；不把它表述为物理附着/搬运 |
| 多源时钟精度是否足以区分标定与时序故障 | 未知 | manifest 强制声明时钟质量；不足时禁止跨源确诊 |
| 大视频和日志的模型上下文成本 | 风险 | 原件保存、索引化、关键帧/片段按需读取 |
| 旧 API 与新 Case 并存带来歧义 | 风险 | 新文档和新 API 明确标记 Case 为重构入口；M5 再删除旧路径 |

M1 已具备资产清单、命令入口和故障/正常两次真实运行记录；下一步是以导出的脱敏 bundle 为材料推进产品端
环境层实现。
