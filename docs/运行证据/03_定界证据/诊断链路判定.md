# 诊断链路判定

视觉链路被切成八段。核心五段任何视觉系统都有；后三段只在视觉输出被执行机构消费时才存在，
本案属于这种情况，所以八段全在。

每一段只有三种状态：`untested`（还没查）/ `cleared`（已排除）/ `suspect`（有嫌疑）。
**非 untested 的判定必须引用证据**，引用的证据必须是宿主真正交付过的——
产品在记账时强制这一条，引用没读过的证据会被丢弃。

| 段 | 判定 | 引用证据 | 依据 |
|---|---|---|---|
| 工件与来料 | untested | — | 两件工件摆放位置不同，来料状态无明显异常，但无专门证据排除。 |
| 光学成像 | cleared | EV-020、EV-044、EV-004、EV-027 | RGB 图像清晰无遮挡，深度有效比 >68%，相机内参一致（焦距554.26，无畸变）。 |
| 采集与时间链路 | untested | — | 两次抓取呈现相同偏差模式，不太像取图同步问题，但未单独验证时间戳。 |
| 视觉算法 | cleared | EV-002、EV-003、EV-025、EV-026 | 算法正确检测到工件位姿并完成 camera→base 坐标转换，XY 精度高。算法检测逻辑无缺陷。 |
| 任务结果 | cleared | EV-022、EV-046、EV-051 | 两次评估均报 missed_pick_pose，position_error ~70mm，与变换链重算的 Z 轴偏差一致，如实反映了现场。 |
| 标定配置 | cleared | EV-054、EV-055、EV-048、EV-050 | camera_to_base 标定参数正确计算了 XY 位置（两件 XY 误差均 <2mm）。tool0_to_tcp 数值 [0,0,0.035] 本身合理，问题在于代码对它的使用次数。 |
| 变换接口 | suspect | EV-054、EV-055、EV-050、EV-056 | flange_command_for_tcp() 对 inverse(tool0_to_tcp) 累积调用了 3 次（compensated → overcompensated → return），正确只需 1 次。多出 2 次 inverse 导致法兰指令在工具轴方向偏低 2×35mm=70mm，与两件实测误差（72mm/70mm）完全吻合。 |
| 机器人侧 | cleared | EV-021、EV-045、EV-003、EV-026 | 机器人实际法兰与指令法兰高度吻合（A: 指令Z=0.253 vs 实际Z=0.255；B: 指令Z=0.253 vs 实际Z=0.253），伺服跟踪正常。 |

## 值得注意的两段

`工件与来料` 和 `采集与时间链路` 留在 `untested`。模型在备注里写明了理由：
没有专门证据可以排除。**它没有为了让链路好看而给出没有依据的 cleared**——
这正是产品要的行为。

## 诊断门

```json
{
  "diagnosis": {
    "passed": true,
    "reasons": []
  },
  "source_visible": true
}
```

门的三个条件：至少一段被指认、至少一段被排除、至少一个假设挂着证据。
三条都满足才放行，放行之后源码工具面才对模型开放（门前 2 件工具，门后 5 件）。
门是代码算的，不是人声明的，也不是模型说了算。
